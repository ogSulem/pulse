# Pulse — архитектура платформы

Документ описывает целевую архитектуру и то, как она соотносится с текущим кодом в этом репозитории.

- **Сейчас в репозитории** — работающий *модульный монолит* (Node.js + SQLite), который целиком закрывает конвейер и панель. Он специально повторяет границы будущих сервисов: каждый этап — отдельный модуль/обработчик задачи с узким контрактом.
- **Целевая production-схема** — те же модули, разнесённые по контейнерам, с Postgres, RabbitMQ и S3. Переезд не требует переписывать логику: меняются адаптеры (БД, очередь, хранилище, провайдеры).

### Компоненты и ответственность

| # | Компонент | Задача | Ключевые данные | Масштабирование |
|---|-----------|--------|-----------------|-----------------|
| 1 | **Web / BFF** | SPA-панель, вход, агрегация экранов, live-статусы (SSE/WS) | токен сессии | stateless, N реплик |
| 2 | **Project Service** | проекты, ниши, продукты, настройки ритма, A/B | `projects`, `products` | stateless |
| 3 | **Content Brain** | идеи, сценарии, описания, хештеги, риск-скоринг | `ideas`, `scripts` | stateless, очередь на LLM |
| 4 | **Render Service** | нарезка, субтитры, TTS-дорожка, стикеры, логотип, сборка mp4 | `renders`, файлы в S3 | горизонтально, CPU/GPU пулы |
| 5 | **Publishing Service** | слоты, квоты аккаунтов, A/B-варианты, публикация | `publications`, `accounts_daily` | 1 воркер на аккаунт |
| 6 | **Analytics Service** | сбор метрик площадок, агрегаты, CTR, эффективность тем | `metrics_daily`, материализованные view | по расписанию, N воркеров |
| 7 | **Accounts & Quota** | пул аккаунтов, статусы, лимиты, прогрев, резерв | `accounts` | stateless + Redis-локи |
| 8 | **Scheduler** | расчёт слотов, джиттер, перенос при перегрузке | `jobs` / RabbitMQ delay | singleton + лидер-лок |
| 9 | **Provider Gateway** | единый адаптер к LLM / видео / TTS / переводу / площадкам | ключи из Vault | stateless, circuit breaker |
| 10 | **Media Storage** | S3/MinIO: исходники, финал, обложки, звук | метаданные в БД | внешний сервис |
| 11 | **Audit / Logs** | журнал действий и ошибок, трассировка задач | `logs` | append-only |

**Почему видео-движок подставляется без переделки:** конвейер знает только контракт
`submit(prompt, params) → externalId`, `poll(externalId) → {status, url}`.
Смена NVIDIA NIM на Runway/Luma/Pika — это новый файл-адаптер в `providers/`, без изменений в этапах конвейера.
В коде это ровно так и сделано: `server/src/providers/index.js`.

### Где это живёт в текущем репозитории

| Модуль | Файл | Будущий сервис |
|--------|------|----------------|
| Очередь | `server/src/core/queue.js` | RabbitMQ + scheduler |
| Этапы конвейера | `server/src/engine/pipeline.js` | Render / Publishing workers |
| Идеи и тексты | `server/src/engine/brain.js` | Content Brain |
| Провайдеры | `server/src/providers/index.js` | Provider Gateway |
| REST API | `server/src/modules/api.js` | API + BFF |
| Журнал | `server/src/core/logger.js` | Audit service |
| Схема БД | `server/src/core/db.js` | Postgres + EF Core миграции |
| Панель | `web/src` | тот же SPA |

## 2. Поток данных: от старта до первых публикаций

**User story «первый запуск» (5–7 минут):**

1. Пользователь открывает панель → вводит `PULSE_PASSWORD` → попадает на «Обзор».
2. Создаёт проект: **название** + **ниша** (2 поля). Опционально — ссылка на продукт.
   → `POST /api/projects` сохраняет проект и сразу генерирует 6 тем под нишу.
3. Смотрит темы, правит хук или сразу жмёт «В конвейер» / «Запустить конвейер» с числом роликов.
   → `POST /api/pipeline/run` создаёт эпизоды и задачи в очереди.
4. Дальше всё идёт само:
   - `episode.prepare` → сценарий по сценам, хештеги, описание, риск-скоринг;
   - `episode.render(voice)` → TTS-дорожка;
   - `episode.render(footage)` → запрос в видео-движок (адаптер);
   - `episode.render(edit)` → сборка, субтитры, логотип;
   - решение: `scheduled` (автопилот) или `review` (риск/ручной режим);
   - `episode.publish` → выбор аккаунта, квоты, слот → публикация → `publications`.
5. В «Очереди роликов» видно каждый этап и прогресс. Спорный ролик можно поправить и подтвердить.
6. Аналитика начинает наполняться: `analytics.tick` раз в несколько минут забирает метрики площадок
   и складывает **приросты за день** в `metrics_daily`. Сводные графики, CTR, подписчики, эффективность тем.
7. Автопилот следит, чтобы в очереди всегда было `2 × posts_per_day` роликов, и добирает темы.

**Что видит пользователь в каждый момент** — таблица состояний:

| Статус | Что происходит | Что может сделать |
|--------|----------------|-------------------|
| `queued` | задача ждёт воркер | изменить сценарий/описание |
| `generating` | идут этапы, прогресс 26→84% | поставить на паузу |
| `review` | ждёт подтверждения (риск ≥ порога или ручной режим) | подтвердить, переписать, отклонить |
| `scheduled` | стоит в слоте | перенести, опубликовать сейчас |
| `published` | вышел, собираются метрики | смотреть статистику, сделать A/B-вывод |
| `failed` | исчерпаны попытки | повторить, поправить, удалить |
| `paused` | снят вручную | вернуть в конвейер |

**Ключевой принцип:** состояние живёт в БД, а не в памяти процесса. Каждый переход — отдельная задача
с `lease` и счётчиком попыток. Рестарт контейнера не теряет работу: `recoverStale()` возвращает
просроченные lease в очередь, `sweepDueEpisodes()` досоздаёт задачи публикации.

## 3. Стек технологий (под ваш .NET / Docker / EF Core)

### Базовый (рекомендуемый) — production

| Слой | Технология | Почему |
|------|-----------|--------|
| API / BFF | **.NET 8 Web API (minimal APIs)** + Swagger | ваш стек, быстрый старт, OpenAPI из коробки |
| Слой данных | **EF Core 8 + Npgsql**, миграции | типобезопасные запросы, миграции в CI |
| БД | **PostgreSQL 16** (Docker) | JSONB для сценариев/метрик, партиционирование `metrics_daily` |
| Очередь | **RabbitMQ 3.13** (quorum queues) + `MassTransit` | at-least-once, retry-политики, dead-letter, отложенные сообщения |
| Кэш / локи | **Redis 7** | rate limit площадок, локи слотов, короткие статусы |
| Медиа | **MinIO / S3** | видео и аудио не место в БД |
| Рендер | **ffmpeg** в отдельном worker-контейнере | нарезка, субтитры, сведение TTS |
| Планировщик | **Quartz.NET** или MassTransit scheduler | cron + отложенные публикации |
| Секреты | **Vault** (или Docker secrets / env для малого контура) | токены аккаунтов не в коде и не в git |
| Фронтенд | **React + Vite** (этот репозиторий) или Blazor | SPA уже готова, отдаётся тем же контейнером/nginx |
| Наблюдаемость | Serilog + OpenTelemetry → Grafana/Loki, Sentry | трассировка задачи по `traceId` |
| CI/CD | GitHub Actions: build → test → docker → ghcr → SSH deploy | один пайплайн на все сервисы |
| Прокси / TLS | Caddy или Nginx | HTTPS, gzip, базовые заголовки |
| Оркестрация | Docker Compose (1 VPS) → **k3s** при росте | начинать с compose дешевле |

### Минимальный контур (этот репозиторий)

Node.js 22 + Express 5 + React 19 + SQLite (WAL). Одна команда `docker compose up -d --build`,
том `./data`, никаких внешних сервисов. Это осознанный выбор для «поставить на VPS и пользоваться»:
SQLite держит десятки тысяч записей и десятки задач в минуту без настройки. Когда понадобится
несколько инстансов — переезд на Postgres описан в `docs/DATABASE.md`.

### Как это ложится на вашу текущую архитектуру

```
Было:  BFF (.NET)  →  API (.NET)  →  Postgres (Docker)

Стало:
BFF (.NET) ── /pipeline/*, /analytics/* ──► Pulse API (.NET, новый сервис)
   │                                             │
   │ аутентификация, агрегация экранов           ├─ EF Core → Postgres (новая схема pulse.*)
   │                                             ├─ MassTransit → RabbitMQ
   │                                             └─ S3 / Vault
   └── SPA (React) отдаётся BFF или отдельным nginx
```

Практические решения:

- **Новый сервис `Pulse.Api`**, не «прикручивать к существующему API». Причина: у конвейера свой темп
  релизов и свои фоновые воркеры; так вы не ломаете текущий продукт.
- **Схема `pulse`** в той же Postgres — миграции EF Core с `MigrationsHistoryTable("__pulse_migrations", "pulse")`.
- **BFF остаётся лицом** для SPA: он проксирует `/pulse/*` и добавляет вашу текущую авторизацию.
  `Pulse.Api` доверяет BFF по внутреннему JWT/MTLS и не публикуется наружу.
- **Воркеры — отдельный процесс** `Pulse.Workers` (MassTransit consumers): его можно рестартовать и
  масштабировать независимо от API. На одном VPS это второй контейнер из того же образа с другим `CMD`.
- **Swagger** включается на `/swagger` только во внутренней сети; наружу — через BFF.
- **Общие вещи**: одно и то же подключение к Postgres, один Vault, один стек логов (Serilog → Loki).
- **Фронтенд** можно отдавать из BFF как статику (`wwwroot`) — тогда CORS не нужен вообще.

## 4. Безопасность и стабильность

| Риск | Мера |
|------|------|
| Утечка токенов площадок | Vault / Docker secrets; в БД только ссылка на секрет; токен читается в момент публикации |
| Пароль панели | `PULSE_PASSWORD` + HMAC-подписанные сессии (14 дней), rate limit 12 попыток/мин на IP |
| Перебор / брутфорс | лимит попыток входа, `timingSafeEqual`, отсутствие подсказок в ответе |
| Потеря задач при падении | `jobs` с `lease_until`, `attempts`, `dead-letter`; восстановление на старте |
| Дубли публикаций | `transactional outbox` + idempotency key (`episode_id` + `variant`); повторная публикация отсекается проверкой статуса |
| Сбои внешних API | retry с экспоненциальным backoff (10с → 40с → 160с), circuit breaker в Provider Gateway, лимит 4 попыток |
| Ошибки в рендере | эпизод помечается `failed`, ошибка видна в UI, есть кнопка «Повторить» |
| Разрастание БД | ретеншн логов (2000 записей), партиционирование `metrics_daily` по месяцам, архивирование видео в S3 lifecycle |
| Несанкционированный доступ к API | все маршруты кроме `/health`, `/covers`, `/auth/login` — за токеном |
| Утечка при экспорте | CSV/JSON-выгрузки требуют токен, содержат только данные владельца |

## 5. Обход блокировок: архитектурно, без «трюков»

Платформа **не** занимается обходом правил площадок. Она снижает риск блокировки за счёт
предсказуемого, «человеческого» поведения и запаса мощностей:

1. **Разделение трафика по аккаунтам.** Публикация идёт на аккаунт с наибольшим остатком квоты
   и лучшим показателем качества. Один аккаунт никогда не получает всю нагрузку.
2. **Временные окна и интервалы.** У каждого аккаунта свой `window_start/end` и `min_gap_min`.
   Слоты двигаются с джиттером ±12%, чтобы не выглядеть секундным таймером.
3. **Лимиты площадок.** Дневная квота (`daily_limit`, глобальный `max_daily_per_account`),
   прогрев новых аккаунтов (1 публикация в день), пауза в `cooldown`, полный стоп в `blocked`.
4. **Ручная верификация.** Риск-скоринг ищет запрещённые формулировки («гарантируем доход»,
   «100%», медицинские обещания). Всё выше порога — в статус `review`, публикация только после клика.
5. **Резервные аккаунты и быстрое переключение.** Статус меняется одним кликом; нагрузка
   автоматически перераспределяется, а задачи публикации переносятся, а не форсируются.
6. **Официальные API.** Публикация через Meta Graph API и TikTok Content Posting API, а не через
   браузерную автоматизацию — меньше причин для санкций и стабильнее.
7. **Прозрачность рекламы.** В описании всегда есть ссылка и понятное указание на продукт,
   без маскировки. Это снижает жалобы и риск ограничений.

Что **нельзя** автоматизировать полностью (и это учтено):

- верификацию личности и подтверждение аккаунта при регистрации;
- прохождение капчи/2FA при подозрительной активности;
- апелляции при блокировке — только человек;
- модерацию площадки: решение принимает платформа, не вы;
- изменение алгоритмов и охватов — можно только измерять и адаптировать темы.

## 6. Риски и ограничения платформы

| Риск | Влияние | Как снижаем |
|------|---------|-------------|
| Правила площадок меняются | публикация ломается | адаптеры провайдеров + feature-флаги, ручной режим как fallback |
| Ограничения API (квоты, ревью приложения) | задержка запуска | бюджет 2–4 недели на аппрув Meta/TikTok, начинаем с одного аккаунта |
| Стоимость видео-генерации | юнит-экономика | лимит на проект, кэш промптов, выбор «дешёвый/дорогой» движок на сценарий |
| Качество AI-сценариев | репутация канала | библиотека форматов + правки в один клик + A/B по темам |
| Дубли контента между аккаунтами | санкции площадок | разный монтаж/озвучка/обложка на аккаунт, ротация шаблонов |
| Перегрузка одного аккаунта | блокировка | квоты, интервалы, автоперенос при исчерпании |
| Рост медиа-хранилища | стоимость | S3 lifecycle: исходники 7 дней, финал 90 дней, обложки бессрочно |
| Единая точка отказа (1 VPS) | простой | volume-бэкап, healthcheck, compose restart, позже k3s + реплика Postgres |
| Юридические требования к рекламе | штрафы | маркировка рекламы, честные формулировки, ручная проверка спорных роликов |

## 7. Экономика и монетизация (как заложено в продукт)

- **Трафик на свои проекты** — каждый сценарий строится вокруг продукта, ссылка с UTM идёт в описание.
- **CTR и клики** — отдельные метрики в аналитике, чтобы видеть не только охваты, но и переходы.
- **A/B-тесты** — два варианта обложки/описания на одном аккаунте; победитель определяется по охвату,
  результат влияет на подбор следующих тем.
- **Подбор тем по эффективности** — «Что заходит» и «По темам» показывают средний охват формата/темы;
  автопилот берёт темы с высоким скором.
- **Партнёрские ссылки** — продукт хранит `utm_source/medium/campaign`; в live-режиме сюда же
  добавляется партнёрский параметр, а клики считаются по редиректу `/r/:id` (описано в API).
- **Экспорт** — темы, сценарии и статистика выгружаются в CSV/JSON: данные не заперты в платформе.

## 8. Рендер-конвейер v3 (слойный монтаж, 1080×1920)

Каждый эпизод на этапе `edit` собирает настоящий вертикальный mp4 1080×1920 @ 30 fps и две обложки.
Своего кодировщика нет — используются готовые компоненты.

| Шаг | Инструмент | Что делает |
|-----|-----------|-----------|
| Фон | `sharp` (librsvg) | один SVG-макет 1080×1920: градиент, сетка, виньетка, «зерно» кодом |
| Типографика | `fontkit` + TTF | текст переводится в векторные контуры: не зависит от шрифтов системы и fontconfig |
| Текстовые слои | `sharp` | каждый текст — отдельный прозрачный PNG поверх фона (без «перерисовки» всей сцены) |
| Движение | `ffmpeg` zoompan | один медленный наезд камеры на фоне: `min(1.07, 1+0.07*on/bgFrames)` |
| Склейка | `ffmpeg` overlay + alpha-fade | слои живут ровно свою сцену, стыки перекрыты на 0.07 с |
| Звук | `ffmpeg` loudnorm | громкость приводится к −16 LUFS / TP −1.5; без TTS — валидная тишина (`anullsrc`) |
| Кодирование | libx264 high@4.1 + aac | `+faststart`, GOP = 2 с — мгновенный старт в ленте |
| Обложки | `sharp` JPEG | два варианта A/B с разными палитрами и бейджами |

Почему слои, а не «пересборка сцены»: раньше каждая сцена растеризовалась целиком, и при ошибке в
таймлайне два текста оказывались в одном кадре. Теперь фон рисуется один раз, а слой существует
`[start, start+d]`, до и после — прозрачен (`tpad` + `fade alpha`). Физически наложиться нечему.

Важная деталь (`engine/scene.js`): подпись-тема над заголовком рисуется только если она *не совпадает*
с текстом сцены (`labelUseful`), а сама подпись — первые 3 слова заголовка с многоточием. Иначе в кадре
появлялся дубль заголовка («3 ОШИБКИ: КАК ПЕРЕСТАТЬ ОТ» над тем же текстом).

### Пресеты качества

| Пресет | Размер | CRF | Аудио | Когда |
|--------|--------|-----|-------|-------|
| `high` (дефолт) | 1080×1920 @ 30 | 19 | 192k | прод: Reels/TikTok нативно принимают 1080p |
| `balanced` | 1080×1920 @ 30 | 22 | 160k | слабый VPS, много роликов в час |
| `fast` | 720×1280 @ 30 | 23 | 128k | черновики и превью, не для публикации |

Env: `PULSE_RENDER_QUALITY=high|balanced|fast` (пресет), плюс точечные `PULSE_RENDER_W`,
`PULSE_RENDER_FPS`, `PULSE_RENDER_CRF`, `PULSE_RENDER_PRESET`, `PULSE_RENDER_AUDIO`,
`PULSE_RENDER_MAX_SEC` (42 с), `PULSE_MEDIA_DIR`, `PULSE_RENDER=off`.

Замер на 2 vCPU: 4 сцены × 4 с = 16 с → рендер ≈ 27 с, файл ≈ 1 МБ. Рендеры сериализуются
(`renderChain`), чтобы ffmpeg не отбирал ядра у API; метрики `render_ms` и `video_bytes` пишутся в эпизод.

Деградация: если ffmpeg/sharp недоступны или файла нет, эпизод уходит в `review` с причиной,
а не публикуется «вслепую» (guard в `engine/pipeline.js`). Кадры не берутся из стока — фон и графика
генерируются кодом, поэтому нет вопросов по правам.

В .NET-контуре это отдельный воркер `Pulse.Render` (SkiaSharp/ImageSharp + FFmpeg), читает задания
из очереди `render`, складывает файлы в S3/MinIO. Контракт тот же: на входе эпизод и сцены,
на выходе путь, размер, длительность и время рендера.

## 9. Комплаенс площадок и «вирусный скор»

Два отдельных сервиса, оба вызываются на этапе `edit` и доступны как API до публикации.

**`engine/compliance.js`** — правила, проверяемые до публикации: обещания дохода, медицинские обещания,
запрещённые категории, кликбейт, маркировка рекламы, лимиты описаний и хештегов. Часть правил блокирующие,
часть — предупреждения. Отчёт сохраняется в `episodes.compliance` и виден в списке, в карточке ролика и
на экране «Прозрачность».

**`engine/viral.js`** — прозрачная эвристика по 6 признакам (хук, длительность, темп, удержание,
описание и теги, новизна темы) с весом каждого и рекомендациями. Это не «предсказание алгоритма» —
в отчёте прямо указано, что модель эвристическая, а порог из настроек (`min_viral_score`) решает,
публиковать автоматически или отдать человеку.

Лимиты площадок заданы как данные (`PLATFORM_RULES`) и проверяются по фактическому потреблению:
TikTok — 15 постов/сутки на креатора, 6 init/мин, неаудированный клиент только `SELF_ONLY`;
Instagram — 50 API-постов в скользящем окне 24 ч, контейнер живёт 24 ч.

## 10. Деньги: как считается доход

`engine/money.js` — единственный источник финансовых цифр.

```
доход = (просмотры / 1000 × RPM площадки)      # реклама площадок
      + Σ конверсий × (цена × маржа)            # продажи по ссылкам
      + Σ начислений по бренд-кампаниям         # спонсорские интеграции (v5)
расход = Σ себестоимости роликов (видео + TTS + LLM + рендер)
прибыль = доход − расход
ROI = прибыль / расход × 100
```

- клики фиксируются короткой ссылкой `/t/<token>` (запись в `clicks`) и увеличивают счётчик публикации;
- покупки приходят на `POST /api/postback` от CPA-сети или платёжки (идемпотентно по `external_id`);
- в demo-режиме клики и конверсии симулируются из счётчиков площадок — чтобы экран «Деньги» был живым,
  но модель оставалась той же, что и в проде;
- себестоимость эпизода пишется один раз и делится между A/B-публикациями.

В .NET: `Pulse.Billing` (или модуль в BFF) с теми же таблицами `clicks`/`conversions`, отдельный
эндпоинт postback и materialized view для сводок.

## 11. Публикация: реальные API, токены и лимиты

Публикация — единственное место, где платформа обязана быть честной: лучше не опубликовать, чем нарушить
правила площадки или «словить» бан аккаунта.

**Токены.** `core/secrets.js` — AES-256-GCM (`enc:v1:iv:tag:data`), ключ = `sha256(PULSE_SECRET + '::pulse-tokens')`.
Токен попадает в БД только в зашифрованном виде, наружу не отдаётся никогда: API возвращает
`has_token`, `token_hint` (последние 4 знака) и `connected`. Подключение — `POST /api/accounts/:id/connect`,
отзыв — `DELETE`, остаток квоты — `GET /api/accounts/:id/limit`. В проде тот же контракт реализуется
через Vault/`IDataProtector`, а не через собственный ключ из env.

**TikTok** (`providers/social/tiktok.js`): Direct Post — `init` → PUT чанком с `Content-Range`
(≤64 МБ одним куском) → ожидание `publish_id`. Неаудированный клиент может публиковать только `SELF_ONLY`,
поэтому приватность берётся из настроек (`tiktok_privacy`), а не из UI-мечтаний. Коды `spam_risk_*`,
`reached_active_user_cap`, `rate_limit_exceeded`, `access_token_invalid` классифицируются: лимит → перенос,
бан → кулдаун аккаунта на сутки.

**Instagram** (`providers/social/instagram.js`): `content_publishing_limit` → `media` (`media_type=REELS`,
`video_url` с публичного `PULSE_PUBLIC_URL`, `cover_url`) → ожидание `FINISHED` (до 5 мин) → `media_publish`.
Планируем по 50 постов в скользящем окне 24 ч (документация расходится 50/100 — берём строгую границу).
`code 9 / subcode 2207042` — терминальный лимит, ретраи только вредят.

**Обработка в `engine/pipeline.js`.** Ошибка классифицируется провайдером и приходит как
`kind='limit'` (перенос на 60–120 мин + re-enqueue) или `kind='ban'` (`accounts.status='cooldown'`,
`blocked_until = +1 день`, публикация переезжает на другой аккаунт того же проекта).
Ни одна публикация не теряется: у неё всегда есть статус и причина.

**Live-аналитика.** `collectAnalytics()` (async) для подключённых аккаунтов тянет фактические метрики
(TikTok video/query, Instagram insights plays/likes/comments/shares/saved) и перекрывает ими модель роста;
дельта пишется в `metrics_daily` как `${publicationId}:${day}`. Если токена нет — остаётся demo-модель,
и в интерфейсе это видно.

**Что нельзя автоматизировать (и почему это нормально).** Верификация бизнес-аккаунтов, аудит клиента
TikTok, модерация площадок и блокировки — внешние процессы. Pulse даёт честный статус, ручную отправку
и кулдауны, но не обещает «обойти» проверку: это и есть антибан-стратегия.

## 12. Интеллект: расписание, прогноз, A/B и обучение

Четыре контура, которые превращают конвейер из «публикует что-то по расписанию» в систему, которая
считает деньги и учится на собственных результатах. Все они объясняют свои решения в журнале и в API.

### 12.1. Умное расписание (`engine/schedule.js`)

Время публикации — не «через 12 часов от предыдущей». Слот выбирается по трём источникам:

1. **Окна аккаунтов** — `window_start`/`window_end` и таймзона. Ночью не публикуем, даже если «пора».
2. **Приоры площадок** — часы активности: Reels — обед и вечер (11–13, 18–21), TikTok — утро, обед, вечер.
3. **Свои данные** — охват по локальному часу публикации, нормированный на медиану проекта
   (медиана, а не среднее: один «залетевший» ролик не делает час лучшим).

Смешивание управляется числом наблюдений: до 8 постов на час вес приора выше, дальше данные доминируют
(но не более 70%). `lift` ограничен 0.75–1.3 — иначе шум превращается в «лучший час». Слот ставится на
`HH:07`, а не на ровный час, чтобы расписание не выглядело ботом.

Ответ `planSlot()` содержит `at`, `hour`, `score`, `source` (`prior` | `data` | `fallback`), `samples`,
`window`, `timezone` и человеческую `reason`. Эта же строка показывается в календаре и в журнале
(`autopilot.fill`), поэтому всегда видно, **почему** ролик вышел именно в 19:07.

### 12.2. Прогноз и умные деньги (`engine/forecast.js`)

```
база      = медиана охвата проекта на площадке за 45 дней (иначе площадка, иначе 1200)
охват     = база × viralFactor(0.75…1.35) × hourFactor(0.4…1.2) × accountFactor(0.6…1.4)
доход     = охват/1000 × RPM + охват × CTR × CR × цена × маржа
прибыль   = доход − себестоимость ролика            ROI = прибыль / себестоимость
```

Все множители и исходные ставки возвращаются в ответе — цифру можно проверить и оспорить, а не «верить».
`target_views` публикации пишется из этого прогноза, поэтому аналитика и прогноз говорят на одном языке.

`projectHealth()` считает факт за 14 дней и выдаёт одно из четырёх решений:
`scale` (ROI ≥ 250% — можно чаще), `hold`, `fix` (ROI 0–40%), `pause` (убыток).
`autopilotPolicy()` меняет `posts_per_day` в пределах 1–6 и **каждое изменение** пишет в журнал с ROI.
Есть предохранитель: если суммарный темп проектов подходит к вместимости аккаунтов (85% от суммы
`daily_limit`), «масштабирование» превращается в `hold` — иначе это были бы бесконечные переносы.

`recalculateAccountQuality()` пересчитывает качество аккаунта по фактическому среднему охвату
относительно медианы площадки (сглаживание 60/40). Дальше `pickAccount()` сам отдаёт нагрузку
аккаунту, который реально приносит охват, — без ручных настроек.

### 12.3. A/B, который заканчивается решением (`engine/abtest.js`)

Тест закрывается через 20 часов после публикации: сравниваются охват и CTR вариантов A и B,
z-тест пропорций даёт уверенность, разница < 8% фиксируется как `tie` (честно, а не «победил A»).
Победитель пишется в `episodes.ab_winner`/`ab_meta`. `preferredVariant()` считает, какой стиль
выигрывает у проекта, и **следующие одиночные публикации сразу выходят в выигрышном стиле** —
проигравший вариант больше не съедает половину охвата.

A/B запускается только когда публикуем на одну площадку: иначе это удвоение квоты, а не эксперимент.

### 12.4. Вирусный скор, который учится (`engine/viral.js`)

Приоры весов (хук 0.30, длина 0.16, темп 0.14, удержание 0.18, описание 0.12, новизна 0.10) уточняются
на своих данных: `recalibrate()` делит ролики по медиане каждого фактора внутри проекта и сравнивает
нормированный охват «верхних» и «нижних». Вес растёт там, где разрыв больше, но не более чем втрое —
один успешный ролик не перекашивает модель. Веса нормируются к 1 и лежат в `settings.viral_weights`.
В отчёте видно `weightsSource`: «приоры» или «обучены на N роликах». Пересчёт идёт в умном цикле
раз в час (когда накопилось ≥ 12 роликов) и доступен руками — `POST /api/insights/recalibrate`.

### 12.5. Мультиплатформенная публикация

Ролик уходит на **все** площадки, где есть свободный аккаунт, а не на одну: у каждой свой caption,
приватность и квота. Если на площадке нет свободной квоты, публикация ставится в повтор через ~30 минут,
а уже вышедшие площадки не дублируются (проверка по `publications`). Баны и лимиты одной площадки
не мешают остальным.

### Границы

Всё перечисленное — статистика на собственных данных, а не «гарантия вирусности». При малой выборке
система честно говорит «приоры» и не притворяется, что знает; в интерфейсе это подписано.

## 13. Рекламный контур (v5): бренды, маркировка, деньги

Реклама — не «вставка», а отдельный поток данных, который проходит через весь конвейер.
Это то, чего обычно не хватает контент-платформе: бренд приходит, договаривается, платит — и всё
это живёт в системе, а не в переписке.

### 13.1. Путь кампании

```
бренд + договор  →  campaigns (бюджет, модель, сроки, erid, бриф)
        ↓
   pickCampaign / autofill          ← учитывает бюджет, дневной кэп, дедлайн, свободные выходы
        ↓
   episodes.campaign_id + ad_disclosure
        ↓
   decorateCaption (edit/publish): @бренд, хештеги, «#реклама», «Реклама. ООО «…». ИНН … erid: …»
        ↓
   checkCompliance: ad-marking-missing / ad-erid-missing / ad-erid-not-in-caption
        ↓
   публикация → campaign_posts (1 выход = 1 публикация, снимок просмотров и кликов)
        ↓
   recordDelivery (авто-done при выполнении posts_target)
        ↓
   syncCampaignMetrics → начисления по модели оплаты (жёсткий потолок — бюджет)
        ↓
   engine/money.js → revenueSponsor → прибыль, ROI, дебиторка, разрезы по проектам и площадкам
```

### 13.2. Почему модели оплаты именно такие

| Модель | Кто так платит | Что важно для платформы |
|--------|----------------|-------------------------|
| `fixed` | малый бренд, «пост за N ₽» | ставка делится на `posts_target`, чтобы каждый выход имел свою цену и прогноз |
| `cpm` | performance-кампании | доход зависит от охвата → работает связка с умным расписанием и вирусным скором |
| `cpa` | CPA-сети, приложения | конверсии приходят из postback; бюджет — потолок, иначе один вирусный ролик «съедает» весь контракт |
| `barter` | бартер за вещи | деньги 0, но выходы, дедлайны и маркировка учитываются так же строго |

### 13.3. Маркировка как блокирующее правило

Реклама без маркировки — штраф, а не «стиль». Поэтому это не подсказка, а проверка комплаенса:

- `ad-marking-missing` (**block**) — в описании нет пометки «Реклама», а кампания её требует;
- `ad-erid-missing` (**block**) — у кампании `marking = erid`, но нет токена ОРД;
- `ad-erid-not-in-caption` (**warn**) — токен есть, но в описание ещё не попал (Pulse добавит при публикации).

`decorateCaption()` идемпотентна: повторная обработка описания не создаёт второй блок маркировки,
поэтому ручная правка и автопубликация не конфликтуют.

### 13.4. Спонсорские деньги в P&L

- начисления считаются по факту выхода (`campaign_posts.revenue_cents`), а не по обещаниям;
- оплата (`paid_cents`) — отдельный факт: она уменьшает дебиторку, но не доход;
- в «Деньгах» появляется третий канал дохода (`revenueSponsor`), а также блок «Спонсорские кампании»
  с начислено / к оплате по каждому бренду;
- в «Рекламе» — дедлайны, остаток бюджета, CPM и ROI каждой кампании.

### 13.5. Автоматизация без человека

- `autofillCampaigns()` вызывается в `autopilot.tick` и раскладывает активные кампании по свободным роликам
  с учётом дневного кэпа и остатка бюджета;
- `recordDelivery()` закрывает кампанию автоматически, когда все выходы сделаны;
- `syncCampaignMetrics()` вызывается после сбора аналитики и пересчитывает начисления из фактических цифр;
- всё логируется (`campaign.attached`, `campaign.autofill`, `campaign.delivered`) — видно, почему ролик получил спонсора.

### 13.6. Как это ляжет на .NET

| Здесь (Node/SQLite) | В production |
|---------------------|--------------|
| `engine/ads.js` | `Pulse.Advertising` (домен: `Brand`, `Campaign`, `Delivery`, `Invoice`) |
| `adsOverview()` | query-эндпоинт в BFF + materialized view по начислениям |
| `pickCampaign` / `autofillCampaigns` | фоновый воркер + outbox-событие `CampaignSlotRequested` |
| `syncCampaignMetrics` | consumer метрик площадок, идемпотентный по `publicationId` |
| `campaigns` / `campaign_posts` | те же таблицы в Postgres, EF Core-конфигурация по DDL из `docs/DATABASE.md` |
| маркировка и комплаенс | правило в `Pulse.Compliance`, блокирует публикацию на уровне состояния эпизода |

## 14. Рост (v6): несколько аккаунтов, Shorts и путь к деньгам

Запрос «вести пару-тройку аккаунтов на TikTok и YouTube и чтобы залетало» разложен на четыре
механизма, у каждого — своя таблица данных и свой экран. Ни один из них не обещает вирусность:
они показывают, что именно мешает охвату **сегодня** и что исправить первым.

### 14.1. Портфель: аккаунт как объект управления

`engine/growth.js → portfolio()` собирает по каждому аккаунту: подписчиков (`accounts.followers`,
обновляется из API площадки), охват за 30 и 7 дней, медианное удержание, остаток квоты на сегодня,
интервал, окно публикаций, `health` 0..100 и **одно следующее действие**.

Аккаунт привязан к бренду (`accounts.project_id`): контент FitFlow не уходит в аккаунт Momentum —
это разные подписчики и разные ожидания. Универсальные аккаунты (`project_id IS NULL`) подходят
любому проекту, поэтому миграция старых баз ничего не ломает. `pickAccount()` фильтрует кандидатов
по проекту, а A/B-тест запрашивает сразу два слота квоты — иначе аккаунт с остатком «1» молча
превышал собственный дневной лимит.

`health` = статус (30%) + качество аккаунта (30%) + удержание против бенчмарка площадки (25%) +
регулярность против планового темпа (15%). Из него выводится `nextAction`: «продолжать темп»,
«менять хуки», «дать отдых», «прогрев 1 пост в день», «квота выбрана».

Портфель считается по площадкам (`platforms[]`) — так видно, что, например, TikTok отстаёт по
удержанию, а Shorts недобирает объём, и решение принимается по площадке, а не по всему проекту.

### 14.2. Лаборатория хуков: первые 1.3 секунды

`hookLab({ topic, platform })` собирает 7 шаблонов (контрадикция, число, вопрос-боль, ошибка,
результат вперёд, петля, ответ на вопрос), подставляет тему и оценивает каждый:

- `hookScore` — сила по паттернам (число, вопрос, контраст, результат, петля, любопытство,
  длина в словах), `viralScore` — общий вирусный скор из `engine/viral.js`;
- `fitsWindow` — успевает ли фраза прозвучать до решения о свайпе. Окно у площадок разное:
  TikTok 1.3 с, Reels 1.3 с, Shorts 2.1 с — на Shorts зритель терпит дольше, но уходит резче;
- `guidance` — правила площадки словами: длительность, цель по досмотру, что ставить в первую фразу.

Тема подставляется в кавычках («про «привычки»»), поэтому русская морфология не ломается на любом
роде и числе — это дешевле, чем согласовывать падежи в шаблонах.

### 14.3. Удержание как проверка перед публикацией

`retentionPlan()` — 8 проверок одного ролика: окно хука, сила хука, длительность против идеала
площадки, петля в конце, конкретика, темп сцен, описание, число тегов (Shorts 3–5, TikTok/Reels 5–8).
Прогноз досмотра = база площадки + поправка на хук и петлю − штраф за длину. Итог: `ready` / `tune` /
`rewrite` / `fix`, где `fix` — блокирующая проблема.

`publishGate(episodeId)` сводит в один вердикт `go | fix | block` всё, что мешает выходу:
комплаенс площадки (включая маркировку рекламы), удержание, вирусный скор, прогноз охвата и квоту.
Это то же, что видит автопилот, — человек и движок смотрят на одни и те же цифры.

### 14.4. YouTube Shorts: особенности площадки

- **Отдельного Shorts API нет.** Вертикальное видео ≤ 3 минут автоматически считается Shorts —
  тот же `videos.insert`, что и для обычной загрузки.
- **Квота.** С 1 июня 2026 у YouTube гранулярные бакеты: 100 `videos.insert` в сутки (1 unit),
  100 `search.list`, 10 000 units на остальные методы. Сброс — в полночь по Тихоокеанскому времени.
  Pulse держит собственный потолок ниже: `min(max_daily × 5, 20)` — алгоритму нужен ровный темп,
  а не выжигание суточной квоты за час.
- **Аудит проекта.** До аудита Google проект может загружать только приватные видео. Это правило
  площадки, а не осторожность Pulse: `privacyFor('youtube')` возвращает `public` лишь при
  `settings.youtube_audited = 1`, иначе `private`. Переключатель — в «Настройках».
- **Лимиты полей.** `title` ≤ 100 символов, `description` ≤ 5000 **байт** (а не символов — для
  кириллицы это вдвое меньше), теги ≤ 500 символов. Проверяется в `engine/compliance.js`.
- **Монетизация.** YPP имеет два порога: ранний доступ — 500 подписчиков + 3 публичные загрузки
  за 90 дней + 3 000 часов просмотра **или 3 млн просмотров Shorts за 90 дней**; полная
  монетизация — 1 000 подписчиков + 4 000 часов **или 10 млн просмотров Shorts**. С 1 февраля 2027
  требования удваиваются (20 млн Shorts-просмотров). Shorts-доход — 45% от пула, watch page — 55%.
- **SEO.** У Shorts работает поиск внутри YouTube, поэтому тема и заголовок важнее, чем в TikTok.

### 14.5. TikTok Creator Rewards и регионы

Порог программы — 10 000 подписчиков + 100 000 просмотров за скользящие 30 дней, аккаунт должен быть
**personal** (не business), 18+, оригинальные видео **дольше минуты** с ≥ 1 000 квалифицированных
просмотров в For You. Программа доступна в 8 странах: US, UK, DE, FR, JP, KR, MX, BR — **РФ в списке
нет**. Поэтому в `monetizationPlan()` у программы стоят `regionLimited: true` и `regionNote`,
а UI прямо пишет: деньги в РФ-аккаунте дают бренд-интеграции и свой продукт, а не выплаты платформы.
Показывать «100% готово» без этой оговорки было бы обманом.

### 14.6. Путь к деньгам по каналам

`monetizationPlan()` сводит 5 программ: YPP-1, YPP-2, TikTok Creator Rewards, бренд-интеграции,
свой продукт. У каждой — прогресс по каждому условию, ETA по текущей скорости (просмотры в день) и
честный текст про ограничения. Скорость берётся из фактических публикаций за 30 дней, а не из планов.

| Здесь (Node/SQLite) | В production |

## 15. План, аудит и база знаний (v6.1)

Три вещи, которых не хватало портфелю: что конкретно публиковать на этой неделе, что прямо сейчас
мешает охвату и деньгам, и где вообще записаны правила площадок. Все три считаются из тех же данных,
что и конвейер, — поэтому не расходятся с реальностью.

### 15.1. Контент-план (`contentPlan`)

План собирается на 1–28 дней вперёд по каждому бренду и складывается в общий календарь:

- **когда** — лучший свободный час площадки из `bestHours()` (приоры + свои наблюдения), а не «утро понедельника»;
- **на каком аккаунте** — только активный аккаунт этого бренда и только в пределах его `daily_limit`;
- **что** — тема из библиотеки `ideas` проекта (сначала неиспользованные), иначе новая по нише;
- **как** — формат ротируется по фактическим данным: сверху идут форматы с `lift ≥ 1`;
- **чем цеплять** — хук из лаборатории, причём берутся три лучших по кругу, а не один и тот же:
  иначе вся неделя начинается одинаково;
- **сколько** — ожидаемый охват из базы проекта на площадке и доход по RPM площадки.

Расписание площадок зашито как стратегия, а не как ограничение: TikTok и Reels — ежедневно,
Shorts — 4 дня в неделю (3–5 роликов в неделю — оптимум алгоритма Shorts). Если у бренда нет
аккаунта на площадке, слот не создаётся: «фантомные» публикации в плане хуже, чем их отсутствие.

### 15.2. Аудит (`platformAudit`)

Аудит — это список того, что мешает зарабатывать, с ценой вопроса и действием. Проверки:

| Проверка | Важность | Почему это дорого |
|----------|----------|-------------------|
| Shorts без аудита Google | блок | видео уходит приватно, охвата нет вообще |
| TikTok-клиент без аудита | внимание | публикация `SELF_ONLY`, ноль просмотров |
| Аккаунты без токена | внимание | конвейер работает в демо, реальные каналы стоят |
| Бренд без аккаунта на площадке | инфо | половина бесплатного охвата не используется |
| Аккаунт бренда в кулдауне/прогреве | внимание | площадка не получает контент вовсе |
| Удержание ниже нормы площадки | внимание | алгоритм не даёт следующую волну показов |
| Кампания с `erid` без токена | блок | публикация блокируется, риск штрафа |
| RPM не задан | инфо | прогноз дохода занижен до нуля |
| Ролики короче 61 с при готовом Creator Rewards | инфо | программа «пройдена», а выплат не будет |
| Простой аккаунта > 7 дней | внимание | регулярность важнее количества |

Итоговый скор 0–100 считается по весам (блок 34, внимание 12, инфо 4) и совпадает с тем, что видно
на экране: один блокирующий пункт уже опускает платформу ниже 80.

### 15.3. База знаний (`platformKnowledge`)

Единый справочник по площадкам: лимиты API и полей, окно хука, идеальная длина, цель досмотра,
что демотивируется, заметки алгоритма и ссылка на официальную документацию. Числа не дублируются
руками: лимиты берутся из `engine/limits.js` и `engine/compliance.js`, поэтому база знаний не может
рассказывать про 100 публикаций там, где комплаенс разрешает 50.

Отдельно перечислены программы монетизации с порогами и **региональными ограничениями**:
YPP (3 млн / 10 млн просмотров Shorts за 90 дней, с 01.02.2027 — 20 млн), TikTok Creator Rewards
(10 000 подписчиков, 100 000 просмотров за 30 дней, видео > 60 с, 8 стран), бонусы Reels по приглашению.
В блоке «Честные границы» прямо написано, что Shorts-просмотры не конвертируются в 4000 часов,
а регион аккаунта решает, какие программы доступны.

### 15.4. Лимиты в одном месте

`engine/limits.js` — единственный источник правды по лимитам: технические лимиты API (TikTok 15/24 ч,
Instagram 50/24 ч, YouTube 100 `videos.insert`/сутки) и рабочий потолок Pulse
`min(темп × 5–17, лимит API)`. Раньше потолки были продублированы в четырёх местах и расходились:
гейт показывал 50 для Shorts, а публикация упиралась в 20. Теперь пайплайн, прозрачность, гейт
и API аккаунта вызывают `platformCap()`, а smoke-тест сверяет все четыре ответа между собой.

### 15.5. Экономика внутри портфеля

`portfolio()` считает доход каждого аккаунта за 30 дней тремя каналами: показы по RPM площадки,
продажи по его публикациям и спонсорские выходы. Отсюда `profitPerPost` и «лучший аккаунт/площадка» —
решение «куда ставить больше контента» принимается по деньгам, а не по количеству подписчиков.

## 16. Креативный движок и студия (v7)

Платформа больше не «принимает идею и делает из неё титры»: она сама собирает ролик целиком —
хук, структуру сцен, описание под каждую площадку, обложку и закреплённый комментарий —
и объясняет каждое решение цифрой.

### 16.1. Почему хук стал короче

Исследование алгоритмов 2026 (TikTok и Shorts) даёт окно свайпа **1.0–1.3 с**: если смысл
не прозвучал, зритель уходит до того, как ролик начался. Старые шаблоны хуков были на 7–12 слов
(2.8–4.8 с) и **физически не успевали**. Теперь `hookLab` строит короткие шаблоны на 3–5 слов
(1.2–2.0 с), тема для них сжимается до 1–2 слов (`shortHookTopic`), а длинные формулировки
остаются в «альтернативных хуках».

Дополнительно хук получает **+10 за упоминание темы**: без этого в топе всегда оказывались
безликие «Результат за 7 дней», одинаковые у всех ниш.

### 16.2. Длина: от 16 до 65+ секунд без потери смысла

Сцена длиной 3–6 с — норма для короткого ролика, но TikTok Creator Rewards платит только за
видео **дольше 60 с**. Поэтому длина не обрезается «оптимумом»: потолок берётся из
`PULSE_RENDER_MAX_SEC` (по умолчанию 42 с, для Creator Rewards — 65), а структура растягивается
**сценами, а не секундами на титре**: при цели > 44 с планировщик добавляет роли из резерва
(`item1…3`, `minus`, `plus`, `verdict`), избегая повторов, и распределяет время по 9 с.
Финальный CTA не держится дольше 4.5 с — это призыв, а не сцена.

Если нужная длина выше лимита рендера, пакет честно предупреждает: «нужно 65 с, но рендер
ограничен 42 — поднимите `PULSE_RENDER_MAX_SEC`», а не молча отдаёт короткий ролик.

### 16.3. Пакет ролика (`engine/creative.js`)

`buildPackage()` собирает один кандидат: хук → структура по формату (`SHAPES`: problem-solution,
before-after, case, listicle, myth, review, pov, meme) → тайминг (хук ≤ 3.2 с, сцена 3–6 с,
вся длина 16–42 с) → описания для трёх площадок → заголовок, обложка, закреплённый комментарий →
оценки. `studio()` собирает до трёх кандидатов и сортирует их по общему скору
(веса: хук 30 %, вирусность 30 %, удержание 25 %, комплаенс 15 %).

Различия описаний по площадкам — не косметика, а правила:

| Площадка | Что можно | Что нельзя |
|---|---|---|
| TikTok | ссылка в профиле, закреплённый комментарий | кликабельная ссылка в описании, > 2200 симв. |
| Reels | кликабельная ссылка с UTM | текст длиннее 2200 симв. |
| YouTube Shorts | ссылка, теги до 500 симв., заголовок ≤ 100 | описание > 5000 байт |

UTM ставится **под площадку, а не под ролик**: `utm_source=tiktok|reels|youtube`, `utm_content=<ideaId>`.
Иначе переходы с одного канала записывались бы другому.

### 16.4. Продажа по надобности (`promotionDecision`)

Правило 80/20: **один продающий ролик на 3–4 полезных**. Решение принимает движок по факту:
смотрит долю роликов с продуктом за 14 дней и выбирает `direct` / `soft` / `none`.
Новый проект начинается с пользы, «перепроданный» — отдыхает от CTA. Решение фиксируется на
эпизоде (`episodes.promo`), публикация его не пересчитывает: иначе ролик мог бы продать то,
что в сценарии не продавалось.

### 16.5. Что попадает в ролик и в публикацию

Паспорт креатива хранится в `episodes.creative` (хук, оценки, предупреждения, варианты,
описания по площадкам, обложка, комментарий). При публикации `buildCaption()` берёт **готовый
текст нужной площадки**, а не переупаковывает базовый: раньше `platformCaption` накладывался
дважды и в описании оказывались две ссылки и два блока тегов. Маркировка «Реклама»/ИИ и
спонсорский блок добавляются ровно один раз (`withDisclosure`), а в `episodes.description`
остаётся чистый текст.

Для TikTok после публикации ставится закреплённый комментарий со ссылкой — единственный
кликабельный путь к продукту на этой площадке.

### 16.6. Очередь не блокирует планировщик

Раньше тик планировщика ждал `drain(4)`, а рендер ролика занимает ~40–60 с: пока он шёл,
не обновлялась аналитика, не срабатывал автопилот и не восстанавливались зависшие задачи —
со стороны это выглядело как «очередь стоит, обработано 0». Теперь воркер и планировщик
работают независимо, у задачи есть таймаут (`PULSE_JOB_TIMEOUT_SEC`, по умолчанию 420 с),
а `drain()` перед работой возвращает в очередь задачи с истёкшим lease.

`POST /api/pipeline/drain` отвечает сразу (`{started, limit, queue}`), а не ждёт пачку;
синхронный режим доступен через `{"wait": true}`.

## 17. Сериалы (v8): длинные истории, фото-ряд и деньги длинного формата

### 17.1. Зачем отдельный продукт, а не «длинный ролик»

Короткий ролик живёт на хуке и удержании первых трёх секунд. Сериал живёт на арке,
персонажах и крючке в конце серии — это другая механика, и в одном движке она не
уживается: у шортса нельзя растянуть сцену, у серии нельзя уложиться в 42 секунды.

Поэтому в v8 появились отдельные модули:

- `server/src/engine/serial.js` — сценарий: библия, арка сезона, 12 битов, главы,
  аудит оригинальности, прогноз денег;
- `server/src/engine/serialrender.js` — рендер 16:9 фото-рядом и вертикальные нарезки;
- `server/src/engine/series.js` — сервис: БД, озвучка секциями, сборка, публикация,
  экономика;
- `web/src/pages/Series.jsx` — экран «Сериалы».

Короткие ролики (`engine/render.js`, `engine/creative.js`) не тронуты: они работают как
работали, 9:16 и лимит 42 секунды остались их правилами.

### 17.2. Хронометраж выводится из речи, а не наоборот

Первая ошибка наивного подхода: «дай сцене 12 секунд и напиши под неё текст». Текст
получается то короче, то длиннее, темп уезжает в 200 слов/мин, и серия звучит как
ускоренная сводка. Здесь наоборот: движок считает **бюджет слов** (`цель × 2.35 слова/с`),
распределяет его по битам, набирает реплики из банков и собирает сцены примерно по 30 слов
(≈13 секунд на кадр). Секунды сцены = слова / 2.35, а остаток до цели добирается
равномерным масштабом в пределах ±12%. Факт: на 600/780/900/1200 секундах длительность
сходится к цели в пределах 0.3%, темп держится 143–148 слов/мин.

Мид-роллы ставятся **на границе глав** (по факту сцен), а не по теории: реклама не рвёт
кадр, а таймкоды в описании совпадают с видео.

### 17.3. Текст: морфология и запрет на повторы

Банк фраз подставляет локации и предметы в разные падежи, поэтому в движке есть
мини-морфология: `inflect()` склоняет словосочетание («придорожный мотель» →
«в придорожном мотеле»), `nameForm()` — имена («у Тимура», «к Вере»), `plural()` —
числительные («3 секунды», «6 секунд»), `guessGender()` — род героя для глаголов
прошедшего времени. Без этого текст читается как машинный.

Повторы запрещены на двух уровнях: `state.used` не даёт повторить реплику дословно,
`state.fns` не даёт дважды подряд использовать один шаблон, `variantCtx()` меняет
предмет и «свидетеля» от строки к строке. В готовой 15-минутной серии все 120+ сцен
уникальны — это проверяет smoke.

### 17.4. Аудит оригинальности — под правила 2026

YouTube с 16.07.2026 разделил «inauthentic content» на три категории: шаблонный
масс-продакшн, манипулятивные формулы «шок ради просмотров» и ИИ-персоны в чувствительных
темах. ИИ сам по себе не запрещён — запрещён шаблон.

`authenticityAudit()` проверяет ровно то, что отличает сериал от конвейера: есть нарратив
(слов/мин и число сцен), есть арка (логлайн + обрыв), есть связь с предыдущими сериями,
есть маркировка ИИ, меняется визуал, длина под мид-ролл, нет кликбейт-маркеров и нет
копирования соседних серий. Проверки со `severity: block` не «минус балл», а стоп:
дословный повтор соседней серии (similarity ≥ 60%) ограничивает оценку 45 баллами и
вердикт «риск демонетизации».

### 17.5. Рендер: 16:9, фото-ряд, субтитры

`renderSeriesEpisode()` собирает длинное видео иначе, чем `renderEpisode()`:

- **1920×1080** вместо 1080×1920: сериал публикуется обычным видео, а не Shorts;
- **concat-демуксер**: каждый план держит свою длительность (у шортса фон один на весь
  ролик — для 15 минут это слайдшоу и прямое нарушение правил монетизации);
- **свой кадр на каждую сцену** (`buildSeriesPlate`): векторный «фотографический» кадр —
  три плана, свет, туман, зерно, виньетка, кинематографические рамки. 9 типов локаций
  (город, лес, дорога, комната, толпа, тоннель, небо, коридор, вода) и 4 крупности;
- **субтитры отдельным alpha-слоем** по чанкам текста: голос и текст совпадают;
- **озвучка секциями** по ≤3200 знаков (лимиты ElevenLabs/OpenAI) с таймингом по
  фактической длине каждой секции: `buildTimeline()` пересчитывает секунды сцен по
  реальному звуку, а не по сценарной оценке.

Потолок длительности — настройка `series_max_sec` (по умолчанию 1200 с): рендер 15 минут
1080p идёт минутами и не должен ронять VPS. Рендер запускается из API в фоне (`202`),
с `?wait=1` — синхронно (для проверки и CI).

### 17.6. Публикация: видео + плейлист + маркировка

Длинная серия уходит через `youtube.uploadVideo({ format: 'long' })` — ссылка ведёт на
`watch?v=`, а не на `/shorts/`. При первой публикации создаётся плейлист сезона
(`createPlaylist`) и каждая серия в него добавляется (`addToPlaylist`): именно плейлист
«по порядку» + автоплей дают удержание N+1/N ≥ 80%, на котором держится сериальный формат.
В ответе публикации возвращается чек-лист: отметка «Изменённый или синтетический контент»
(через API недоступна, ставится в Студии), главы с 0:00 и оформление Shows для YPP.

### 17.7. Нарезки — это трафик, а не отдельный продукт

Вертикальные нарезки не живут в сериальных таблицах: `pushCutsToQueue()` создаёт обычные
эпизоды в `episodes` со сценами «крючок → тело → полная серия в профиле», описанием с CTA,
`promo: 'soft'` и ссылкой на источник. Дальше работает существующий конвейер: креатив,
комплаенс, лимиты площадок, расписание, публикация, аналитика. Так у сериала два канала:
длинные серии приносят деньги (мид-роллы), короткие нарезки — новых зрителей.

### 17.8. Деньги длинного формата

`revenueForecast()` считает по RPM жанра (`SERIES_GENRES`, ₽/1000: зомби 120–260,
мистика 140–300, нуар 160–340, фантастика 150–320, фольклор 110–240) и даёт сценарии
5k/15k/50k/150k просмотров с часами просмотра. `seriesEconomics()` добавляет путь к YPP
(4000 часов), окупаемость серии (`breakevenViews`) и сколько серий нужно до цели по деньгам.
Себестоимость серии считается по факту: знаки озвучки × `cost_tts_1000` + минуты рендера ×
`cost_render_min` + LLM.

`refreshSeriesMetrics()` обновляет `views / rpm / revenue_cents` опубликованных серий: в live
из YouTube Data API, в demo — по модели роста. Планировщик вызывает её вместе с остальной
аналитикой, поэтому «Деньги» показывают длинный формат отдельным блоком (`moneySummary().longform`)
без ручных действий.

### 17.9. Расписание серий: выпуск без участия человека

Короткие ролики годами выходят через `sweepDueEpisodes()` → задача `episode.publish`. Сериям
нужен тот же контур, иначе «сериал» — это набор кнопок, а не конвейер:

* `scheduleEpisode(id)` переводит собранную серию в `stage = 'scheduled'` (без файла на диске
  отказывает — расписание без видео бессмысленно);
* `sweepDueSeriesEpisodes()` раз в ~20 с ищет `scheduled` с `publish_at <= now`, у которых есть
  `video_path` и нет `external_id`, и ставит задачу **`series.publish`** в общую очередь
  (dedupe-ключ + проверка живой задачи, чтобы не плодить копии);
* обработчик `series.publish` вызывает `publishEpisodeToYoutube()` и при ошибке возвращает серию
  в `review` с текстом ошибки — иначе планировщик повторял бы падение каждые 20 секунд.

Выключается настройкой `series_autopublish = 0` (тумблер в «Настройках»). В demo-режиме
публикация симулируется провайдером, в live — реальная загрузка файла в фоне, поэтому
планировщик не блокирует тик.

### 17.10. Публичный хостинг: что решает boot.js

Платформа ставится на один контейнер (Railway, Render, Fly, Oracle Always Free, любой VPS).
Чтобы это работало без ручной настройки, старт вынесен в `core/boot.js`:

| Решение | Почему так |
|---|---|
| `PORT` → `PULSE_PORT` → `8080` | Railway/Render/Fly передают `PORT`, docker compose — `PULSE_PORT`. Приложение слушает `0.0.0.0` |
| `PULSE_SECRET` из env, иначе генерация в `data/.pulse-secret` (0600) | известный дефолт из репозитория = подделка сессионного токена кем угодно; при этом рестарт не должен разлогинивать |
| пароль из `PULSE_PASSWORD`, иначе на облаке случайный в `data/first-login.txt` (0600) | `pulse` на публичном адресе — это открытая дверь; сгенерированный пароль печатается в лог **один раз** и переживает рестарт |
| локально без облачных переменных — прежний `pulse` | `npm start` после клонирования должен работать без настройки |
| ffmpeg: `PULSE_FFMPEG_PATH` → installer → системный бинарь | `@ffmpeg-installer` есть не под все архитектуры; в Docker ставится apt-ffmpeg, поэтому ARM (Oracle Ampere) тоже рендерит |
| `data` — единственный том | база, медиа, бэкапы и секрет в одном каталоге: переезд = копирование каталога |

Артефакты деплоя в репозитории: `Dockerfile` (ffmpeg + tini + healthcheck), `railway.json`,
`render.yaml`, `fly.toml`, `docker-compose.yml` (+ профиль `tls` с Caddy), `deploy/install.sh`
для чистого сервера, `npm run backup` (консистентный бэкап SQLite через `db.backup()`).
Пошаговая инструкция и сравнение площадок — `docs/DEPLOY.md`.

### 17.11. Студия реального запуска: OAuth, нейро-кадры, автопилот (v9)

Итерация «работаем не в demo, а сразу со своими аккаунтами». Четыре механизма, без которых
это не работает, и один экран, который их объясняет.

**Вход в канал через OAuth (`engine/oauth.js`).** Ручное копирование токена — главный барьер:
он живёт час, его надо продлевать, и он ломает «поставил и забыл». Поэтому у каждой площадки
нормальный поток authorization code + PKCE (S256):

| Площадка | Приложение | Скоупы | Особенность |
|---|---|---|---|
| YouTube | Google Cloud → OAuth Client (Web) | `youtube.upload`, `youtube.readonly` | `access_type=offline` + `prompt=consent`, иначе нет `refresh_token` |
| TikTok | TikTok for Developers | `user.info.basic`, `video.publish`, `video.upload` | в authorize параметр `client_key`, не `client_id` |
| Instagram | Meta App (Instagram Graph) | `instagram_basic`, `instagram_content_publish`, `pages_show_list`, `pages_read_engagement` | видео забирается по публичному URL — нужен `PULSE_PUBLIC_URL` |

`state` живёт в памяти 10 минут и одноразовый: коллбэк `/api/oauth/:platform/callback`
зарегистрирован **до** auth-middleware (площадка не пришлёт сессионную cookie), а защиту дают
state + PKCE. После обмена кода профиль канала тянется из API площадки, аккаунт находится по
`external_id` (или заводится), токены шифруются AES-256-GCM. `ensureFreshToken()` вызывается
перед каждой публикацией и продлевает токен за 3 минуты до истечения; в UI аккаунт показывает
`auth_state: ok | expired | none` и `refreshable`. Redirect URI без `PULSE_PUBLIC_URL` берётся
из origin запроса — это и есть «работу из коробки» на localhost.

**Нейро-кадры (`engine/frames.js` + `providers/image.js`).** Фото-ряд сериала — это то, что
отличает «историю про зомби» от слайд-шоу. Кадр = промпт из сцены (место, план, палитра,
настроение + стиль канала), провайдер, кэш:

- провайдеры по цене: `pollinations` (Flux, без ключа, анонимно ~15 с между запросами, 0 ₽),
  `cloudflare` (Workers AI, 10k нейронов/день бесплатно), затем платные `replicate`/`openai`/`stability`;
- кэш `data/media/frames/<sha1(provider|prompt|WxH|seed)>.jpg` — повторный рендер серии не тратит
  ни лимиты, ни время;
- троттлинг — последовательная очередь с паузой `image.minGapSec()`, иначе анонимный тариф
  отдаёт 429 и серия остаётся без кадров;
- потолок `series_image_max` (60 кадров) — длинная серия не превращается в тысячу запросов;
- отказ любого провайдера **не ломает рендер**: кадр заменяется процедурной плашкой
  (`buildSeriesPlate`), серия всё равно выходит;
- режим задаётся на сериал (`series.frame_mode`) и глобально (`series_frames`):
  `auto` — нейро, если провайдер доступен; `neural` — всегда; `procedural` — только плашки.

**Тема канала как лицо аккаунта.** У аккаунта появились `topic`, `language`, `visual_style`,
`persona`. `createEpisode` берёт тему канала и подменяет ею нишу проекта при генерации идей,
`pickAccountFor()` выбирает канал проекта (или универсальный) с учётом квоты — поэтому один
YouTube-канал про зомби и один про нейро-разборы не размываются в «средний контент».

**Автопилот сериала (`seriesAutopilot`).** Раз в 10 минут сервер держит сочинёнными
`series_lookahead` серий вперёд (по умолчанию 3) и, если у сериала включён `auto_render`,
ставит `series.render` в очередь. Задача `series.render` = `synthesizeEpisode` (озвучка) →
`renderEpisodeById` (кадры + сборка): рендер идёт минутами, поэтому живёт в очереди, а не в тике.
`dryRun: true` считает план без записи — так UI показывает «что будет дальше», не меняя данные.

**Свой продукт в трёх режимах.** `products.placement`: `video` (продукт в кадрах и сценарии,
описание чистое), `caption` (только мягкое упоминание и ссылка в описании), `both`. `always = 1`
отключает дозирование 80/20 — для собственного продукта это осознанный выбор владельца, но
маркировка рекламы (`decorateCaption`, erid/«реклама») остаётся обязательной. В описании серии
продукт упоминается мягко и получает ссылку с UTM через выпуск (`withProduct`).

**Экран PulseStudio (`GET /api/studio/overview`).** Один чек-лист вместо десяти разделов:
подключить канал → задать тему → добавить продукт → запустить контент → перейти в live.
Прогресс считается по весам шагов, `nextStep` — что делать прямо сейчас; рядом состояние
интеграций (нейро-кадры, OAuth по площадкам с точным redirect URI и списком недостающих
переменных, провайдеры, автопилот). Всё, что показано, взято из реальных настроек — экран не
может «врать».

### 17.12. ИИ-слой без счетов: бесплатные модели, бесплатная озвучка, NVIDIA (v10)

Правило итерации: **ИИ везде, где он даёт качество, и ни рубля за это, пока есть бесплатный путь.**
Поэтому слой моделей собран как роутер, а не как «один ключ OpenAI».

| Слой | Реализация | Цена |
|---|---|---|
| Тексты (идеи, сценарии, описания, библия сериалов) | `providers/llm.js`: цепочка `ollama → nvidia → gemini → groq → cerebras → openrouter → mistral → openai` | 0 ₽ на первых шести |
| Озвучка | `providers/tts/edge.js`: Edge TTS (WebSocket-протокол Microsoft), голоса `ru-RU-DmitryNeural`/`SvetlanaNeural` | 0 ₽, без ключа |
| Кадры сериала | `providers/image.js`: Flux через Pollinations, Cloudflare Workers AI | 0 ₽ |
| Видео | `providers/index.js`: NVIDIA NIM (`nvidia/cosmos-…`), затем Runway / Luma / Pika / Replicate | 0 ₽ в рамках ключа NVIDIA |

**Роутер, а не адаптер.** У каждого провайдера свой базовый URL (`<ID>_BASE_URL`), своя модель
(`<ID>_MODEL`) и свой бюджет RPM/RPD. Порядок перебора — сначала бесплатные; жёстко
фиксируется `PULSE_LLM_ORDER` / `PULSE_LLM_PROVIDER`. Ответы кэшируются в `data/ai-cache/<sha1>.json`
на 7 дней: повторная генерация того же промпта не тратит лимит, а демо-прогоны и тесты
не «съедают» бесплатную квоту. `PULSE_LLM_BASE_URL` подменяет адрес **только первого**
провайдера — это нужно для мок-сервера и для шлюзов, и не ломает фолбэк.

**Edge TTS — почему именно он.** ElevenLabs за 15-минутную серию берёт деньги за каждый символ,
а качество русского у Edge TTS выше, чем у любого бесплатного локального синтеза. Протокол
неофициальный, но стабильный: WebSocket `speech.platform.bing.com`, заголовок `Sec-MS-GEC` =
sha256 от округлённых до 5 минут Windows-тиков + публичный токен клиента, формат
`audio-24khz-48kbitrate-mono-mp3`, кадры `speech.config → ssml → audio → turn.end`. Текст режется
на куски ≤2600 знаков по предложениям, mp3 склеивается побайтово — без ffmpeg. Отказ сервиса
(403 из-за расхождения часов, сеть, прокси) не ломает серию: `TTS_PROVIDER` можно переключить на
`elevenlabs`/`openai`, а в demo-режиме тайминг считается по словам.

**NVIDIA NIM как основной ключ.** Бесплатный ключ `build.nvidia.com` закрывает сразу три роли:
LLM (`meta/llama-3.3-70b-instruct`, ~40 запросов/мин), судью-редактора для библии сериала и
видео (`POST https://ai.api.nvidia.com/v1/genai/<model>`). Ответ видео бывает двух видов —
синхронный mp4 и async `id`; адаптер понимает оба и складывает файл в `data/media`.

**Честный статус в UI.** `GET /api/ai/status` отдаёт по каждому провайдеру `configured`, `free`,
`model`, `rpm/rpd`, `callsToday` и `active`; `POST /api/ai/test` делает живой запрос и возвращает
провайдера, модель и миллисекунды. Экран «Настройки → ИИ-движок» показывает это как есть:
что готово, чего не хватает (`keyEnv`), сколько запросов уже израсходовано сегодня.

**Что ИИ делает в конвейере.** Идеи (`/ideas/generate` → `source: 'ai'`), пакет ролика
(`enrichPackage`: хук, сцены, описание, теги), библия сериала (`aiBible`), текст серии
(`aiComposeEpisode`: режет нарратив по сценам пропорционально секундам, пересчитывает WPM и
перезапускает аудит оригинальности) и режиссура кадра. Любой отказ модели — не ошибка платформы:
движок откатывается на детерминированный шаблон, а причина уходит в лог `ai_failed`.

**Честность вместо «демо-шума».** Случайный второй аккаунт в выборе канала и искусственный 429
во время рендера остались только в demo-режиме (и то не в 100 % случаев); в live выбор аккаунта
детерминированный: сначала те, кто сегодня не публиковал этот проект, затем больший остаток квоты,
затем качество и время последней публикации.

### 17.13. Бесплатный стек и запуск «на деньги» (v11)

Требование итерации звучало буквально: **заработать без вложений**. Это не про «добавить ещё
дашборд», а про три вопроса, на которые платформа обязана отвечать сама.

**1. Хватает ли бесплатных ресурсов на полный цикл?** Да, и это зафиксировано в коде:

| Шаг | Бесплатный путь | Ограничение |
|---|---|---|
| Тексты | NVIDIA NIM → GitHub Models → Gemini → Groq → Cerebras → OpenRouter → Mistral | у каждого свой RPM/RPD, роутер перебирает |
| Озвучка | Edge TTS | нет |
| Кадры | Pollinations Flux | ~15 с между кадрами, кэш по промпту |
| Публичный адрес | Cloudflare Quick Tunnel (`deploy/tunnel.sh`) | адрес временный, пока открыт туннель |
| Хостинг | Oracle Always Free (ARM 4 OCPU / 24 ГБ) | ARM-сборка образа |

GitHub Models — важное дополнение: ключ есть у любого, у кого есть GitHub-аккаунт
(fine-grained token с правом `models:read`), поэтому «нет ключа» перестаёт быть причиной не
включать ИИ. Cloudflare Workers AI использует **тот же токен**, что и картинки, — второй ключ
не нужен. Если у Cloudflare не задан `CLOUDFLARE_ACCOUNT_ID`, провайдер не притворяется готовым:
`keyOf()` возвращает пустую строку, и роутер его пропускает (иначе первый же запрос давал бы 404).

**2. Идёт ли работа без человека?** `POST /api/launch/start` включает автопилот целиком
(платформа + серии + кампании + маркировка) и, главное, честно возвращает `blockers` —
что именно мешает заработать (нет подключённого аккаунта, нет продукта, канал без темы, нет сериала).
Идемпотентность проверяется smoke-тестом: второй вызов обязан вернуть пустой список изменений.

**3. Дойдёт ли контент до площадки?** Публикация в Instagram/TikTok идёт не файлом, а ссылкой:
площадка сама скачивает видео по `PULSE_PUBLIC_URL`. Поэтому появилась проверка
`POST /api/launch/check-url`: она делает реальный HTTP-запрос снаружи, проверяет панель и
отдачу `/media` (HEAD на самый свежий файл) и различает три состояния — «адрес не задан»,
«адрес не отвечает», «адрес отвечает, но медиа ломается». Локальный `curl` эту проверку не
заменяет: он ходит изнутри сети, а площадка — снаружи.

**Чего бесплатно не бывает, и платформа это не скрывает.** Выплаты YouTube/TikTok недоступны
аккаунтам из РФ: TikTok Creator Rewards работает в 8 странах, YouTube-партнёрка требует страну
выплат. Поэтому на старте деньги дают три канала, и все три уже посчитаны в «Деньгах»:
свой продукт по ссылке с UTM (клик → конверсия → выручка), партнёрские/CPA-ссылки и
бренд-интеграции (начисления по кампаниям, дебиторка, оплаты).

### 17.14. Себестоимость по факту и единственный канал контроля (v12)

Две вещи, без которых «прибыльность» и «удобство» остаются словами.

**Себестоимость считается по провайдерам, а не по прайсу.** В настройках лежат рыночные ставки
(45 ₽ за видеоряд, 12 ₽ за озвучку, 8 ₽ за LLM) — они нужны, когда владелец платит за сервисы.
Но если озвучка идёт через Edge TTS, кадры — через Pollinations, а тексты — по бесплатному ключу
NVIDIA, реальная себестоимость ролика ≈ 1 ₽ (только процессор). Считать её по прайсу ElevenLabs —
значит показывать убыток там, где его нет, и прятать прибыль. `engine/costs.js` берёт ставки из
настроек и **обнуляет те, что в текущей конфигурации бесплатны**; флаг `powered_by_me = 1`
возвращает прайс (владелец платит за инфраструктуру). Значение используется в трёх местах, где
раньше был дублированный расчёт: `pipeline` (себестоимость ролика), `forecast` (прогноз ROI),
`money` (`costPerVideo` в отчёте) и `series` (ставка за 1000 знаков озвучки серии).

**Telegram как единственный обязательный канал связи.** Автопилот работает сутками; владелец не
сидит в панели. Минимальный бесплатный канал — бот (Bot API бесплатен, создаётся за минуту).
`engine/notify.js` собирает суточную сводку из реальных таблиц: ролики и серии за 24 часа,
просмотры и клики, деньги (кампании + продажи), расписание и очередь ревью, упавшие задачи с
последней ошибкой, блокеры «что мешает заработать». Отправка не бросает исключений: сводка не
важнее конвейера, ошибка площадки просто уходит в журнал. Защита от спама — `last_digest_at`
в настройках: не чаще раза в 20 часов, поэтому рестарты контейнера не дублируют сообщения.
Планировщик проверяет готовность каждые 10 минут и отправляет после 10:00 по часовому поясу панели.

### 17.15. Проверка ссылки продукта: деньги начинаются там, где кликают (v13)

Ролик может быть идеальным, но если ссылка в описании отдаёт 404, домен припаркован или редирект
уводит на чужой сайт, выручка равна нулю — и в панели это выглядит как «контент не заходит».
Поэтому проверка ссылки стоит там, где её видит владелец: в карточке продукта.

`engine/linkcheck.js` повторяет путь зрителя: `GET` с сервера, `redirect: follow`, таймаут 8 секунд,
тело ответа не читается (закрываем поток — незачем тянуть мегабайты картинок). Вердикт трёхуровневый:

- `ok` — открывается по https (редирект внутри сайта допустим);
- `warn` — открывается, но есть замечание: http вместо https, редирект на другой домен (парковка
  домена / чужой сайт), `3xx` без перехода, `401/403/429` (сайт закрыт от ботов — стоит проверить
  руками);
- `error` — `404/410`, `5xx`, таймаут, невалидный адрес.

Рядом возвращается готовая ссылка с UTM (`withUtm`), чтобы было видно ровно то, что попадёт в
описание. Вердикт не теряется между сессиями: он лежит в самом продукте (`link_level`,
`link_status`, `link_checked_at`, `link_note`), поэтому в карточке видно последнюю проверку и
когда она была — без похода в сеть при каждом открытии страницы. Проверка не бросает исключений — вызывающий код не обрастает `try/catch`, а проблемные
результаты пишутся в журнал (`product.link_checked`), поэтому история «когда ссылка сломалась»
восстанавливается по ленте событий.

Тот же код работает в smoke (`проверка ссылки продукта`: живая / 404 / редирект / мусор / таймаут /
UTM) — на локальном сервере, без выхода в интернет, поэтому проверка проходит в CI.

## 18. Хостинг и эксплуатация (v14): один адрес, самодиагностика, чистое место

Три модуля отвечают за то, чтобы платформа вела себя одинаково на ноутбуке, на VPS и на Railway.

### 18.1. `core/publicurl.js` — единственный источник публичного адреса

Раньше адрес собирался в четырёх местах (`oauth.js`, `providers/index.js`, `series.js`, `launch.js`)
и в каждом была своя обработка пустого значения. Это дало реальный баг: на Railway адрес панели
известен платформе, но приложение его не видело и просило «задайте PULSE_PUBLIC_URL».

Теперь приоритет один на весь код:

```
PULSE_PUBLIC_URL → RAILWAY_PUBLIC_DOMAIN → RENDER_EXTERNAL_URL / RENDER_EXTERNAL_HOSTNAME
                 → FLY_APP_NAME (.fly.dev) → KOYEB_APP_NAME (.koyeb.app) → ''
```

- `publicBase()` — `https://host` без хвостового слэша (используется для OAuth-редиректов);
- `mediaBase()` — `…/media` (Instagram забирает ролик по этой ссылке);
- `hostedDomain()` — домен для подписи `Host` в OAuth-колбэках;
- `publicSource()` — какая переменная сработала (видно в `/api/health` и в студии);
- `isHosted()` — на облаке ли мы (влияет на подсказки «как поставить домен»).

Ручной `PULSE_PUBLIC_URL` остаётся: он нужен для туннеля и для случая, когда домен проксируется
снаружи. Но теперь это переопределение, а не обязательное условие запуска.

### 18.2. `engine/deploy.js` — «будет ли это работать», а не «запустилось ли»

`deployReadiness()` собирает 12 проверок и отдаёт их с `level` (`ok | warn | error`) и `fix`:

| Проверка | `error` | `warn` |
|---|---|---|
| `disk` | каталог данных недоступен для записи (на Railway без тома — тоже блокер) | свободно меньше 1 ГБ |
| `auth` | на публичном адресе пароль не задан | короткий пароль, `pulse` или пароль по умолчанию |
| `public_url` | — | адреса нет (Instagram/TikTok не смогут забрать файл) или он без HTTPS |
| `mode` | — | демо-режим: публикации имитируются |
| `render` | нет ffmpeg/шрифтов — ролики не соберутся | — |
| `media` | в каталог медиа нельзя писать | — |
| `storage` | свободно меньше 500 МБ | больше 20 устаревших файлов |
| `ai` | — | нет ключа, работает встроенный Content Brain |
| `telegram` | — | нет канала уведомлений |
| `autopilot` | — | выключен / настройки недоступны |
| `replicas` | — | больше одной реплики на SQLite |
| `secret` | — | секрет подписи не сохранён на диск |

Тот же отчёт печатается одной строкой при старте (`→ Хостинг: ok 4, предупреждений 5, ошибок 0`),
отдаётся в `GET /api/deploy/ready` и рисуется в студии карточкой «Хостинг и диск». Никаких «сходите
в документацию и догадайтесь»: каждая строка содержит действие.

### 18.3. `engine/housekeeping.js` — место под медиа не заканчивается

Rendered-файлы — самая тяжёлая часть тома (десятки мегабайт на ролик). `storageUsage()` считает
файлы, байты, видео, устаревшие и свободное место (`statfs`), `pruneMedia()` удаляет только медиа
старше N дней и ставит `episodes.media_pruned_at`, `autoPrune()` вызывается из `index.js` раз в
6 часов. Строки, метрики и публикации не трогаются — история и деньги остаются, диск освобождается.

Как это ляжет на .NET:

| Здесь (Node) | В production |
|---|---|
| `core/publicurl.js` | `HostingOptions` + `IPublicUrlResolver` (конфигурация + переменные платформы) |
| `engine/deploy.js` | health-check эндпоинт `DeploymentReadinessController` + те же правила в `IHostedService` |
| `engine/housekeeping.js` | `BackgroundService` + `IMediaPruner`, дата удаления — поле в `episodes` (EF Core) |
