# Pulse — план реализации (MVP за 4–6 недель)

Цель MVP: **пользователь запускает конвейер и через сутки у него есть опубликованные ролики,
переходы на продукт и понятная статистика.** Всё, что не нужно для этого результата, откладывается.

Роли в команде: 1 backend (.NET), 1 frontend, 1 «движок»/DevOps (может совмещаться).
Если разработчик один — сроки ×1.6, и тогда сначала закрываем «тонкий» срез (см. ниже).

---

## Спринт 0 — подготовка (2–3 дня, идёт параллельно)

- [ ] аппрув приложений Meta (Instagram Graph) и TikTok Content Posting — **подать в первый день**,
      это самый длинный внешний процесс;
- [ ] VPS: Docker, домен, HTTPS (Caddy), бэкап-скрипт каталога `data`/дампа Postgres;
- [ ] репозитории `Pulse.Api` / `Pulse.Workers` / `Pulse.Web`, CI: build → тесты → docker → ghcr;
- [ ] схема `pulse` в Postgres, `dotnet ef` миграции, тестовые данные;
- [ ] ключи провайдеров (LLM, TTS, видео) в Vault, лимиты расходов на аккаунтах.

## Неделя 3 — публикация, слоты, аккаунты

**Результат недели:** ролик выходит сам, аккаунты не перегружены.

| Задача | Критерий готовности |
|--------|---------------------|
| Accounts & Quota | лимиты, окна, прогрев, cooldown, blocked, резерв |
| Scheduler | слоты с джиттером, перенос при перегрузе, «на паузу» |
| Publishing Service | OAuth-токены из Vault, идемпотентная публикация, вебхуки статусов |
| A/B | два варианта на одном аккаунте, разные обложки/описания |
| UI: календарь + очередь | перенос слота, отмена, публикация сейчас, ручное подтверждение |
| Антиблок-правила | квоты соблюдаются в 100% публикаций (тест на симуляторе) |

**Демо:** 3 ролика уходят на 2 аккаунта по расписанию, панель показывает статусы и ссылки.

## Definition of Done (для каждой задачи)

1. Работает на чистой базе: `docker compose up` → миграции → данные.
2. Есть обработка ошибок и запись в журнал; повтор не ломает данные.
3. Проверено на «плохих» данных: пустая ниша, битая ссылка, 429 от провайдера.
4. UI: пустое состояние, загрузка, ошибка, мобильная ширина.
5. Обновлены `docs/` и `.env.example`, если появились новые параметры.
6. Есть бэкап-совместимость: новые поля — nullable или с дефолтом.

## Риски сроков и что делать

| Риск | Признак на 1-й неделе | Реакция |
|------|----------------------|---------|
| Не дали доступ к API площадки | аппрув Meta/TikTok не пришёл | публикуем вручную по напоминанию, API включаем позже |
| Видео-провайдер нестабилен | >10% ошибок | два адаптера + переключение по флагу, дешёвый fallback |
| Сценарии «плоские» | пользователь переписывает всё | усиливаем библиотеку форматов и few-shot на своих лучших роликах |
| Сроки поехали | 2 недели без демо | режем A/B и расширенную аналитику, оставляем базовый цикл |

## Тонкий срез, если разработчик один (10–12 дней)

1. Проект + темы + сценарий (LLM) — 2 дня.
2. Очередь + статусы + панель-очередь — 2 дня.
3. Озвучка + шаблонный рендер (ffmpeg, без видео-нейросети: b-roll/стоковые кадры) — 3 дня.
4. Публикация в один аккаунт Reels + календарь — 2 дня.
5. Аналитика «охваты/клики/CTR» + CSV — 2 дня.
6. HTTPS, бэкап, документация — 1 день.

Этот срез уже приносит трафик и данные, а видео-нейросети подключаются адаптером позже —
ровно так, как устроен текущий репозиторий.

### Что делать в первые 3 дня после выката

0. Подключить три канала к своим брендам: в «Аккаунтах» у каждого аккаунта выбрать проект —

1. Подать заявки в Meta (Instagram Graph), TikTok Content Posting и Google (YouTube Data API) — аудит занимает недели,

2. Снять 3 метрики «как есть»: RPM по площадкам, CTR ссылки, конверсию в покупку — и проставить их

3. Прогнать 5 роликов вручную: проверить файл, обложку, описание, постбек-ссылку. Только после этого

## v14. Хостинг и эксплуатация: «разворачивается легко и везде»

| Блок | Статус | Где |
|---|---|---|
| Railway одной командой | ✅ | `deploy/railway.sh`: проект → секреты → том → деплой → `/api/health` |
| Railway по шагам для человека без CLI | ✅ | `docs/RAILWAY.md` (дашборд + CLI, тарифы, откат, сбои) |
| Публичный адрес без настройки | ✅ | `core/publicurl.js`, блок `hosting` в `/api/health` |
| Готовность хостинга вместо «запустилось» | ✅ | `engine/deploy.js`, `GET /api/deploy/ready`, карточка «Хостинг и диск» |
| Один каталог данных | ✅ | `core/paths.js` (`PULSE_DATA_DIR` → база + медиа + секрет) |
| Диск не заканчивается | ✅ | `engine/housekeeping.js`: авто-уборка раз в 6 часов, `media_pruned_at` |
| Два режима compose | ✅ | локальный (`up -d`) и `--profile tls` (Caddy + `PULSE_DOMAIN`) |
| Конфиги не расходятся с кодом | ✅ | smoke: `railway.json` × Dockerfile × compose × `.dockerignore` × маршруты API |
| База знаний о площадках | ✅ | часы публикаций, экономика 1000 просмотров, чек-лист первой недели |

### Решения, которые стоит помнить

1. **Один публичный адрес на весь код.** Любая новая функция, которой нужен адрес панели, обязана
   брать его из `core/publicurl.js`. Прямое чтение `process.env.PULSE_PUBLIC_URL` — регрессия:
   именно так ломался Instagram на Railway.
2. **Один каталог данных.** Новые файлы состояния (кэш ИИ, бэкапы, логи) кладём внутрь
   `DATA_DIR`/`MEDIA_DIR`, а не в `process.cwd()`, иначе они окажутся вне тома.
3. **Проверка вместо совета.** Если что-то можно проверить кодом (том, пароль, адрес, ffmpeg,
   место), это делается в `engine/deploy.js` с полем `fix`, а не описывается в документации.
4. **Одна реплика на SQLite.** Горизонтальное масштабирование — только после переезда на Postgres;
   `deploy.js` предупреждает, если реплик больше одной.
5. **Уборка медиа не трогает историю.** Удаляются только файлы; строки, метрики и деньги остаются,
   поэтому отчёты и ROI не «прыгают» после чистки.

## v15. Простота: пять разделов, один следующий шаг, защита от расползания

| Блок | Статус | Где |
|---|---|---|
| Меню из пяти разделов с вкладками | ✅ | `web/src/lib/nav.js`, `App.jsx` |
| Первый экран «Сегодня»: один шаг, деньги, что мешает | ✅ | `web/src/pages/Today.jsx` |
| Старые адреса продолжают работать | ✅ | `LEGACY` + `resolveRoute()` |
| Хостинг — отдельная вкладка настроек | ✅ | `components/HostingCard.jsx` |
| Дашборд из десяти блоков убран | ✅ | его работа разошлась по «Сегодня» и «Аналитике» |
| Запуск в Docker на Windows (CRLF) | ✅ | `.gitattributes`, `sed` в Dockerfile, smoke-проверка |

### Решения, которые стоит помнить

1. **Пять разделов — предел.** Новая функция идёт вкладкой в существующий раздел, а не новым
   пунктом меню. Smoke падает, если разделов станет больше пяти.
2. **У каждой вкладки есть экран.** Меню и карта экранов проверяются одним тестом: вкладка без
   компонента — это пустая страница без ошибки в консоли.
3. **Старые адреса не удаляем.** `LEGACY` — часть контракта: закладки, письма, ссылки из
   уведомлений и серверные `action.to`.
4. **Один шаг вместо десяти панелей.** «Сегодня» отвечает на один вопрос и не пытается быть
   витриной всех возможностей.
5. **Скрипты — только LF.** Windows-клонирование не должно ломать запуск контейнера.
